The aggregate beacon address is n-of-n by default, and each script leaf is opt-in (ADR 169).

- aggregation: Breaking: by default, the beacon address has no script tree. The output key is the MuSig2 aggregate key P with the tweak `taggedHash('TapTweak', P)`. Thus only all n members together can spend the beacon UTXO, and each Beacon Signal has a signature of each member. Before, the address always had the k-of-n fallback leaf and the CSV recovery leaf.
- aggregation: Breaking: if the cohort conditions have a `fallbackThreshold` (k), the address has the k-of-n fallback leaf with exactly that k. With no `fallbackThreshold`, the address has no fallback leaf. Before, `computeBeaconAddress` used k = max(1, n-1) if the conditions had no `fallbackThreshold`.
- aggregation: Breaking: `recoveryKey` and `recoverySequence` are optional. If both are present, the address has the CSV recovery leaf. `validateCohortConditions`, `createCohort`, and `isCohortAdvertMessage` refuse a config or an advert with only one of the two. `isCohortAdvertMessage` also refuses a `recoveryKey` that is not 64 hex characters. Before, both values were required, and `isCohortAdvertMessage` checked only that `recoveryKey` was a string.
- aggregation: Breaking: `AggregationParticipant` and `AggregationParticipantRunner` have the options `allowFallbackLeaf` and `allowRecoveryLeaf` (default `false`). `joinCohort` refuses an advert that names a leaf that the participant does not allow, with the error type `FALLBACK_LEAF_NOT_ALLOWED` or `RECOVERY_LEAF_NOT_ALLOWED`. The cohort stays in the Discovered phase. The runner emits `error` and sends no `COHORT_OPT_IN`. Before, the participant joined each cohort that `shouldJoin` accepted.
- aggregation: Breaking: at `COHORT_READY`, the participant refuses a key count below `minParticipants` or above `maxParticipants` of the advert, with the error type `COHORT_SIZE_OUT_OF_BOUNDS`. The phase stays OptedIn. Before, only the service checked these bounds.
- aggregation: Breaking: `startFallbackSigning` refuses a cohort with no fallback leaf, with the error type `NO_FALLBACK_LEAF`. `triggerFallback` of the service runner rejects with this error. With `autoFallbackOnStall`, the runner fails such a cohort at a stall, with `COHORT_PHASE_STALLED`. The participant drops a `FALLBACK_AUTHORIZATION_REQUEST` for such a cohort, before it wipes its secret nonce. Thus the request cannot stop the key-path round.
- aggregation: Breaking: `FallbackSpendParams.fallbackThreshold` is required, and `recoveryKey` and `recoverySequence` are optional. `buildFallbackSpend` refuses a beacon output with no fallback leaf (`PREVOUT_SCRIPT_MISMATCH`). `RecoverySpendParams.fallbackThreshold` names the fallback leaf of the output: omit it if the output has no fallback leaf. If the caller sets `beaconAddress`, `buildRecoverySpend` refuses an output with no recovery leaf (`BEACON_ADDRESS_MISMATCH`). Before, both builders used k = max(1, n-1) if `fallbackThreshold` was absent.
- aggregation: Breaking: `AggregationRunner.solo` adds no leaf by default. `SoloCohortOptions.config` has the new optional `fallbackThreshold`. The solo participant allows each leaf that the config names. Before, if the config did not name the recovery values, `solo` set `recoveryKey` to the x-only key of the service and `recoverySequence` to 144. With no leaf, two solo runs with the same participant key and network get one beacon address. For another beacon type, use another participant key.
- aggregation: Breaking: this change removes these items, with no alias: `resolveFallbackThreshold`, `AggregationCohort.effectiveFallbackThreshold`, and the error type `NO_RECOVERY_PARAMS`. `BeaconLeafParams` requires only `cohortKeys`, and `buildRecoveryLeaves` returns 0, 1, or 2 leaves. The new `recoveryLeafParams` refuses an input with only one of the two recovery values, with the error type `INCOMPLETE_RECOVERY_PARAMS`. `computeBeaconAddress` and `buildRecoveryLeaves` refuse the funding model `participant-funded`, also with no leaf.
