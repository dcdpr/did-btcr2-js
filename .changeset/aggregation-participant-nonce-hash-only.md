'@did-btcr2/aggregation': minor

The aggregation participant makes the SMT nonce and sends only the update hash (ADR 168).

- aggregation: Breaking: the `SUBMIT_UPDATE` body is `{ cohortId, updateHash }`, and `createSubmitUpdateMessage` takes `updateHash` in place of `signedUpdate`. The `updateHash` is 32 bytes in base64url with no padding. In a CAS cohort, it is the JSON Document Hash of the update. In an SMT cohort, it is the leaf value: `hash(hash(nonce) + updateId)` for an update, or `hash(hash(nonce))` for no update. `isSubmitUpdateMessage` accepts only a body with a `cohortId` string and an `updateHash` string. Before, the body was `{ cohortId, signedUpdate }`, and the service got the full update.
- aggregation: Breaking: in an SMT cohort, the participant makes the nonce: 32 random bytes for each round. The participant keeps the nonce and sends only the leaf value. `buildSMTTree` puts the value of each member at the index `hash(did)`. Each proof from the service has only `id`, `collapsed`, and `hashes`. `submitUpdate(cohortId, signedUpdate)` keeps its signature, and the runner `onProvideUpdate` callback does not change. Before, the service made the nonce of each member in `buildSMTTree` and sent it in the SMT Proof of the member.
- aggregation: Breaking: in an SMT cohort, `declineUpdate` makes a nonce and sends `SUBMIT_UPDATE` with `hash(hash(nonce))`. This message has the same form as an update, so the service cannot tell a decline from an update. The participant runner still emits `update-declined`. In a CAS cohort, `declineUpdate` still sends `SUBMIT_NONINCLUDED`. Before, `declineUpdate` sent `SUBMIT_NONINCLUDED` in each cohort, and the service saw that the member had no update.
- aggregation: Breaking: the service checks only the form of the `updateHash`. If the `updateHash` is not a string that decodes to exactly 32 bytes, the service refuses the message with `UPDATE_MALFORMED`. The decoder is strict: it refuses the padding character `=` and padding bits that are not zero. The membership check (`NOT_A_MEMBER`) and the `DUPLICATE_RESPONSE` check stay, in the same order. Before, the service canonicalized the update, checked its size, and checked the structure and the sender of its proof.
- aggregation: Breaking: this change removes these items, with no alias: `BaseBody.signedUpdate`, the `maxUpdateSizeBytes` option and property, `DEFAULT_MAX_UPDATE_SIZE_BYTES`, and the rejection codes `UPDATE_TOO_LARGE` and `UPDATE_SENDER_MISMATCH`. `AggregationServiceParams` and `AggregationServiceRunnerOptions` had the `maxUpdateSizeBytes` option. The service no longer does the sender check of ADR 152, decision 4. The CAS map key or the SMT leaf index `hash(did)` binds the 32-byte value of the body to the DID of the sender. Before, the service refused an update above `maxUpdateSizeBytes` (default 256 KiB) with `UPDATE_TOO_LARGE`. If the proof `verificationMethod` of an update was not a DID URL of the sender, the service refused the update with `UPDATE_SENDER_MISMATCH`.
- aggregation: Breaking: `AggregationCohort.pendingUpdates` is now `updateHashes`, a map of each member DID to its `updateHash` string. `addUpdate(participantDid, updateHash)` takes the `updateHash` string. `AggregationService.collectedUpdates(cohortId)` is now `collectedUpdateHashes(cohortId)`, and it returns that map. `buildCASAnnouncement` puts each `updateHash` in the map as the member sent it. Before, the cohort held the full update of each member (a `SecuredDocument`) and hashed it.
- aggregation: Breaking: `AggregateBeaconStrategy` has the new method `prepareSubmission(updateId?)`. It returns a `BeaconSubmission` (`{ updateHash?, nonce? }`): the value that the member sends and the nonce that the member keeps. If `updateHash` is absent, the participant sends `SUBMIT_NONINCLUDED`. The author of a custom strategy for `registerBeaconStrategy` must add `prepareSubmission`. `validateParticipantView` takes `{ participantDid, updateHash?, nonce?, updateId?, body }`. Before, it took `{ participantDid, included, submittedUpdate?, expectedHash?, body }`.
- aggregation: in an SMT cohort, the participant takes only `id`, `collapsed`, and `hashes` from the proof of the service. It adds its own `nonce`, and the `updateId` for an update, then verifies the proof. `CohortCompleteInfo.smtProof` of the `cohort-complete` event and `PendingValidation.smtProof` are this full SMT Proof. The caller must persist it: the specification says "Participants MUST persist their `nonce` values." Before, the participant verified the proof of the service with the `nonce` that the service made.
- aggregation: the service accepts `SUBMIT_NONINCLUDED` in an SMT cohort, and the index of that member stays empty. The leaf value of that index is `cachedZero[0]`, as the specification gives for no update with no nonce. The library participant does not send this message in an SMT cohort. Before, the service put a leaf with a nonce of the service at that index.
- aggregation: `buildSMTTree` skips a submitted value equal to `cachedZero[0]`. The index stays empty, and the root does not change. A leaf with that value can give another member a sibling hash equal to a cached zero. `verifyProof` returns `false` for such a proof. Before, the service made each leaf from its own nonce, so no leaf had that value.
- aggregation: Breaking: `AGGREGATION_WIRE_VERSION` is 2. The service and the participant do not process a message of another version. The participant also ignores a `COHORT_ADVERT` of another version, so it does not join that cohort. Thus a peer of version 1 and a peer of version 2 cannot complete a round together. The service and each participant of a cohort must use wire version 2. Before, the version was 1.
